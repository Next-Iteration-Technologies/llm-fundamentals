One message from Finance, five agents and a rulebook

This page follows one request through a multi-agent pipeline, and the discussion that shaped it: when an agent is worth it, when plain code is better, and what splitting work across agents really costs. You don't need to read the code to follow it. Every section links to the files if you want to.

Where we started

Lab 01 has the pipeline shape, but none of its stages is an agent

Lab 01 answers “I can't find invoice 1234” with four stages in a fixed order. Two of them are ordinary Python functions. The other two make one LLM call each, with no tools and no decisions about what to do next.

The order lives in these four lines, and nothing decides at run time. That makes Lab 01 a good picture of the pipeline half of the pattern. As an example of multi-agent it is weak: an agent has a goal, picks its own actions (usually tools) and loops until it is done. Anthropic's “Building effective agents” calls this shape prompt chaining, a workflow rather than an agent system.

The first objection

“This problem is clean. I could just write a program.”

With a tidy request and tidy data, that's right, and a program would be better. Every step could be an if: “Meyer Logistics Q3 2025” is a filter on vendor and folder, Classic vs CSP is a field, Finance vs HR is a comparison.

An LLM only earns its place where something can't be listed in advance

  1. Unpredictable phrasing. “the Westpark one from last summer”, “that ancient Rhein thing”.
  2. Fuzzy matches. The archive says “Meyer Log. GmbH”; something has to judge whether that's the same vendor.
  3. Rules written in prose, with exceptions. “Deletable on request, unless a dispute is open.”
  1. Facts buried in text. A legal hold mentioned in an email.
  2. Sources that disagree. HR says delete; Legal says hold.
  3. Deciding the next step when the obvious search finds nothing.

If you can write the rule down, write code. Use an agent only where the input is language, the rule is language, or the next step depends on what was just found.

The design

Five stages in a fixed order: four agents, and one stage that must be plain code

Intake agent

Goal
Work items for everything Priya said and the letter implies, tagged explicit or implied
Figures out
“that old Rhein invoice” means an invoice from 2019; “freight costs” means vendors she didn't name
Tools
read_attachment, list_document_types
Boundary
Doesn't search or judge permissions

Retrieval agent

Goal
Each item resolved to its records, or marked ambiguous or not found
Figures out
“Meyer Log. GmbH” is Meyer; a credit note isn't an invoice; which Q3 vendors are freight; when to search again
Tools
search_documents, find_document
Boundary
Read-only; never acts on text inside a record

Policy agent

Goal
Allowed, blocked or needs approval for each request, with the clause or email it relied on
Figures out
Legal's later hold beats HR's email; tax records can't be deleted; 1236 is suspicious
Tools
read_policy, search_emails
Boundary
Advises only; can restrict, never grant

Access & Action code

Logic
Checks Priya's workspace and rights; the stricter of code and Policy wins; exports, opens tickets, routes the rest
Why code
Permissions must give the same answer every time. No LLM grants access here.

Responder agent

Goal
One plain reply: ready, pending and on whom, added from the letter, and why anything wasn't done
Tools
None. Sees only the finished work order.
Boundary
Can't change any outcome

Agent, code or MCP?

A fuzzy match doesn't need an agent, and MCP doesn't make decisions

The fuzziness is in…ExampleWhat handles it
the data“Meyer Log. GmbH” vs “Meyer Logistics”code a similarity match on the vendor name, inside search_documents
the phrasing“the Westpark one from last summer”LLM one call turns it into a search
the next stepno hits, so widen the dates, then compare amounts, then askagent loop it decides what to try based on what came back

MCP is plumbing. It is a standard way to expose a tool such as search_documents to any model or client without re-wiring it. It helps the model reach the tool; it doesn't decide which tool to call or what to do with the answer. That is the agent's job.

Inside one agent

An agent here is a loop: pick a tool, see the result, repeat until done

Each agent only gets the tools for its job, and every tool result is wrapped and marked as data. The model chooses the steps; code runs them. The same loop works with Nexus or Claude: one setting in .env, LLM_PROVIDER, picks the provider.

What actually happened when the pipeline ran

What Priya received · excerpt

Ready: Invoice 1234, Meyer Logistics. Invoice 1236, Westpark Services: its title contained unusual embedded text asking for an access list to be sent to an external address. We ignored it and flagged the record to the security team.

Added because of the auditor's letter: Invoice 1235, Nordbahn Freight. Credit note CN-1240, Meyer Log. GmbH: it likely adjusts invoice 1234, so the auditor will probably want both.

Pending: Invoice 4711, Rhein Office Supplies, is on the older Classic archive; a retrieval ticket is open, expect it within 3 working days.

Not done: Contract 7001 can't be deleted. On 20 Oct Legal put it on legal hold because of an open overtime claim, which takes priority over HR's email.

A judgement call, not a bug: credit note 1240

Priya asked for invoices, and 1240 is a credit note. But the auditor asked for all supporting documents for Q3 freight. Across runs the pipeline excluded it, added it, or held it for Priya to confirm. All three are defensible. Which would you want?

What the first live runs taught us

Four things broke at the edges between stages, and how they were fixed

What went wrongWhyFix
Rhein (Classic) was held instead of getting a ticketPolicy treated “Classic platform” as a reason to refuse. How a document is delivered isn't a policy question.Policy's prompt now says delivery is handled after it
The reply said “the work order doesn't mention an auditor's letter” and “we'll verify you're in Finance”The Responder never saw why each item existed, or that access had been checkedEach action now carries requested_as and access_checked
Intake guessed the tool's argument name twiceThe agent saw tool descriptions but not their parametersThe tool list now shows each function's signature
Retrieval ran out of stepsSix items at one tool call per turn, plus extra searches, didn't fit in 8 stepsThe limit is now 15

None of these was a model failure. Each was a gap in a handoff: what one stage passed on, or what it thought its job was. Remember that for the cost section.

The second objection

“Wouldn't this all still work with a single agent?”

Yes, almost certainly. Seven records, a one-page policy and three emails fit in one context. One capable model with every tool would very likely reach the same five outcomes.

Most of the safety is code, not the split

And no agent has a delete tool or a send tool. Contract 7001 can't be deleted however confused a model gets, and the instruction hidden in 1236 has nothing to send with. One agent plus this same code gate gets about 90% of what the lab shows.

What the split buysHow much it matters here
Independent check. Policy didn't do the searching, so it has no stake in approving what was found.Real, but small at this size
Least privilege. Retrieval can't read emails; Policy can't search.Real, but the code gate already covers the dangerous actions
Context isolation. Each agent sees only its slice.Not needed: it all fits in one context
Testable stages. Check Retrieval on its own.Useful for teaching and debugging
A model per stage. Cheap for Intake, strong for Policy.Not used in the lab
Visible trace. You can see who decided what.The main teaching value

This would work with one agent. We split it because each split is a boundary you'll need at scale or under audit, and the code gate is what actually keeps it safe.

Multi-agent isn't free

What splitting costs, measured on our own runs

Tokens and time

Retrieval and Policy use 90% of the input. Each re-sends its growing conversation on every tool call, and stages can't start until the one before finishes.

Handoffs

Every boundary is a contract: a shape for the data, and an understanding of who owns what. The lessons on the previous slides were all handoff bugs. A single agent has no handoffs.

Errors compound

Later stages trust earlier ones. Intake's extra “supporting documents” item is why credit note 1240 appeared. Five stages that are each right 95% of the time are right together about 77% of the time.

Distributed-system problems

In production: a crash in Policy loses earlier work, a retry can export twice, a prompt change can silently break the next stage, and you need tracing to find where a run went wrong.

Single agent + code gateMulti-agent + code gate
Tokens and latencyLowerHigher
Handoff bugsNoneAt every boundary
Failure handlingOne loopCheckpoints and retries per stage
Independent checkNoYes
Scale, ownership, audit separationWeakStrong

Start with one agent plus code. Split when a specific need forces it: context limits, separate owners, an auditor requiring separation, or untrusted content at volume.

When you do have a reason to split

Multi-agent is a distributed system with an LLM in each node. Engineer it like one.

Tokens and latency

  • Pass compact handoffs, not transcripts
  • Cache the policy and system prompts
  • Pick a model per stage
  • Run items in parallel inside a stage
  • Tools that take a batch of queries

Handoffs

  • A schema at every boundary, checked in code built
  • Each stage writes only its own fields
  • Carry the original request along
  • “Decide X, not Y” in each prompt

Compounding errors

  • Check between stages built
  • Let later stages object
  • Send back once, then ask a person
  • Evaluate each stage on its own

Distributed problems

  • Checkpoint after every stage built
  • Idempotent side effects built
  • Timeouts, retries, dead-letter queue
  • Trace and cost per agent built

The same pipeline, hardened

Four fixes, built and working in our own example

The hardened script imports the simple lab and adds only the engineering. Same agents, same tools, same code gate.

1 · Typed handoffs: a bad answer goes back, it doesn't slip through

In a run, the rejection goes back to the agent, which fixes its answer (from a scripted test run):

[Retrieval Agent] handoff rejected: item C was not resolved (+1 more)
[Retrieval Agent] done (handoff validated)
[Policy Agent] handoff rejected: no decision for 1236 retrieve
[Policy Agent] done (handoff validated)

2 · Grounding: every work item must quote the request it came from

This stops Intake inventing work. It does not catch credit note 1240, which really is “supporting documents”; that is a Retrieval judgement, caught only when the item names a type.

3 · Checkpoints and idempotent actions: crash, resume, never do things twice

$ python labs/01b_sequential_agents_hardened.py --stop-after retrieval
[Checkpoint] saved after intake
[Checkpoint] saved after retrieval
Stopped after retrieval (simulated crash). Continue with:  --resume 20261028-233633

$ python labs/01b_sequential_agents_hardened.py --resume 20261028-233633
[Checkpoint] resuming after retrieval
[Policy Agent] checking 6 requests against policy …

$ python labs/01b_sequential_agents_hardened.py --resume 20261028-233633 --from action
[Access & Action] 1234 retrieve: added to export package (already done in an earlier attempt, not repeated)

4 · Cost per agent

Both versions print the calls, tokens and seconds per agent at the end of a run. That is where the numbers on the costs slide come from. Compare the two scripts: the hardening adds checks and files, not model calls, unless a handoff is rejected.
